# EC2 続き　
## OSを管理者権限で操作できる
- 起動したec2インスタンスでは、AWS symple managerのセッションマネージャーやsshを使用してosを管理者権限で操作できる。
  - sshとは自分のpcからec2サーバーに安全にアクセスするためのもので鍵を持つ。また、そこからターミナルで操作していく。
  - セッションマネージャーとはAWS symple managerの中の機能の一つでsshを使用しなくてもec2サーバーにアクセスできる
### セッションマネージャー
AWSsymplemanagerの機能の一つ。三つの前提条件のもとで使用できる。
- 使用条件
  - SSMAgentがOSにインストールされている。
    - SSMAgentはほとんどのクイックスタートAMIに入っている。
    - SSM Agent = EC2とAWS管理サービスをつなぐ橋でEC2の中で動く小さなプログラム

  - EC2インスタンスがsystemmanagerで管理できるようにIAMロールを引き受けている
  - EC2インスタンスからのリクエスト送信がSystemMnagerのエンドポイントに到達できる
- OSに安全に接続できて、管理者権限で操作できる。

# 5-2ELB
## ELB の概要
- Elastic load Balancig
- Desin for FailureのアンチパターンでEC２インスタンスを複数のアベイラビリティーゾーンに配置してユーザーから単一アクセスを受け付けるようにする
- <img width="550" height="467" alt="image" src="https://github.com/user-attachments/assets/9c868eec-9662-49f9-945e-534799ddc6c4" />
### EC2インスタンスの可用性、耐障害性を高めるためにELBを使う
## ELBの特徴
- ロードバランサータイプ
- ヘルスチェック
- インターネット向け/内部向け
- 高可用性マネージドサービス
- クロスゾーン負荷分散
  ## ロードバランサータイプ
  - ELBには4つのタイプがある＊ここでは２つ
    - application Load Balancer: httpまたはhttpsのリクエストを負荷分散する用途で選択。webappicationに対して高度な機能が提供される
    - network Load Balancer:Http,Https以外の時に選択する
    - ALBにない機能は性的なipアドレスを使用できる。1秒あたり数百万のリクエストを処理できる
  ### http/httpsではALBそれ以外ではNLBを使う

## 3/23
 ## ヘルスチェック
 - ELBはインスタンスが正常かどうかヘルスチェックする
 - パスへの接続試行で状態を確認する
 ## インターネット向け/内部向け
 - ELBは外部内部どっちかを選択する
 ### インターネット向けELB
 - パブリックipアドレスが付与され外部からインターネット接続できる。
 ### 内部向けELB
 - DNSにプライベートipアドレスが付与され外部からは受け付けず内部での接続を許可する

 ###  インターネット向けだけでなく内部もELBを挟むことによってシステムの可用性をさらに高められる。
 ## 高可用性のマネージドサービス
 - ELBを使うことでEC2の高可用性を実現できる、よってELBは単一障害点ではないのか？
   ### 違う
   - ELB自体が高い可用性を持ったマネージドサービス
   - ユーザからのリクエストが増えればその分ELBのノードも増えて対応する

# 5-3 AutoScaling
## 設定
- 何を={起動テンプレート}=どのようなEC2インスタンスを起動する
- どこで={AutoScalingグループ}=どこでEC2インスタンスを起動するか
- いつ={AutoScalingポリシー}=どのタイミングで起動終了するか
### 起動テンプレート（なにを）
- AMI
- インスタンスタイプ
- IAMロール
- ユーザーデータ
- すとれーじ
- セキュリティタイプ
### AoutScalingグループ（どこで）
- 起動テンプレートとバージョン
- アベイラビリティーゾーン
- ELBのターゲットグループ
- 最小最大希望するインスタンス数
### AoutScalingポリシー(いつ)
- 動的スケーリング
  - ターゲット追跡スケーリング
    - EC2インスタンスのCPU平均使用率などを決めておく、最も簡単な設定方法。
    - https://docs.aws.amazon.com/ja_jp/autoscaling/application/userguide/target-tracking-scaling-policy-overview.html
  - ステップスケーリング
    - CloudWatchアラームに基づいて柔軟に設定したい場合使う
- 予測スケーリング
- 過去の実績をもとに機械学習し必要なインスタンスを予測し事前に起動できる

## アプリケーションデプロイの自動化
- AoutScalingでは起動テンプレートを予め用意して、AMIをもとにEC2インスタンスが起動するから再現性が高い。だけど必要なくなればスケールインされ、EC2インスタンスは削除されるのでEC2インスタンスに情報を持たせない設計が必要。
- この構成をステートレスという
### ブーストラップ
- 複数のリージョンで同じアップデート設定をしてる場合同じ作業が必要だがそれを解決するのがブーストラップという設計パターン
 ### ユーザーデータ
 - EC2インスタンスの初回起動時に自動実行するもの
  - 最新バージョンのプログラムをダウンロード
  - EC2インスタンスのパブリックipアドレスを取得して設定ファイルに書き込む
 ### メタデータ
 - パブリックipアドレスやインスタンスIDなど、インスタンスを起動しないと生成されない情報を取得できる

 ### EC2のユーザーデータを使うことでコマンドを自動実行し、デプロイ処理を自動化できる

## Lambdaの概要と特徴
- <img width="1133" height="448" alt="image" src="https://github.com/user-attachments/assets/c59a1b9a-0d8b-40e0-86c5-bb8f06583afa" />
- プログラムの開発や最適化に集中できる
## サーバーの構築が不要
- Lambdaではサーバーの構築が不要ですぐに開発ができる
## サーバーの管理が不要
- セキュリティーパッチの適用、エラーのリトライ、ミドルウェアなどのメンテナンス、ディスク容量の追加などが不要
### 開発に注力できる
## 言語
- pythonやcなど使い慣れた言語でLambdaを使える
## 並行処理とスケーリング
- リクエストがない場合は実行されない
- 同時にリクエストが発生した場合はLambda関数が同時に実行される。
### 自動的に水平にスケーリングされ、並行で関数が実行される
- なのでAoutScalingする必要はない
## 柔軟なリソース設定
- Lambdaで設定する性能はメモリだけで範囲は１２８MG --10230MB
- CPU性能はメモリに比例して設定される
## 無駄のない課金
- 実行されてる時間に対してミリ秒単位の課金がされる
